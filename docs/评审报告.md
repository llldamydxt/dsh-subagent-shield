## 一、总体结论

**这个插件的判定核心是可靠的。** 用一份**独立重写的真值机**（`测试\oracle.mjs`，不 import 插件任何代码）对 **18000 组**输入逐项比对：

```
混淆矩阵（正类 = 应当拦）
  TP = 6840    TN = 11160
  FP = 0       FN = 0
  一致率 = 100.0000%
```

**零假阳性、零假阴性。** 历史那 5 次「拿不到确定目标 → 回落到宽松默认」的漏口（`glob/grep` 的 `pattern` 参数、目录级路径、通配符 token、豁免工作区的目录级列举、`settingsScope` 服务名），在这次穷举里一个都没有复现。

命令族也符合它自己的声明：**13 条应命中全部命中，12 条误伤检查零误伤，8 条已声明的绕过（`[char]` 拼接 / base64 / 变量拼接 / `Join-Path` / 反引号 / `cmd /c` 套壳）全部如实放行** —— 我没有把"能绕"当成缺陷，因为 README 自己就写了。**把已知残余风险断言为"绕过"，比假装拦住更有价值。**

但有三处该修：一处是**保护面的真空**（P1，唯一被测试台判红的功能项）、一处是**性能随规则条数线性劣化**（P2，6400 条规则时单次判定 3.6 ms）、一处是**它自己新开的无鉴权清单接口**（P3）。

> 关于「规则条数」这条要说清楚：**出厂配置下完全没有这个问题**（规则表为空，单次判定 ~20 µs）。P2 只在用户按设置页的设计意图**逐条点名**到上千条时才浮现 —— 而这恰好是这个插件最推荐的用法。

## 二、缺陷清单

### 🔴 P1 —— 自定义账本路径时，默认账本失去保护（保护面真空）

**证据**（`selfRoots(home, auditFile)` 的第 3 条只保留当前 `auditFile` 指向的那一个路径）：

| 配置 | `read <DSH_HOME>\subagent-shield-audit.jsonl` |
|---|---|
| `auditFile` 留空（默认） | **拦** [state] |
| `auditFile` 指向自定义文件 | **放行** ← 缺陷 |
| `auditFile` 为空白串 | 拦（走兜底） |

**为什么严重**：插件在关掉"记录新拒绝"或换了账本文件之后，**历史账本仍然躺在默认路径上**，里面含别的工作区路径、窗口 id、工具调用目标 —— 是元数据。此时子代理可以读取它。这与你已经在代码注释里写下的设计原则**直接矛盾**：

> `// 账本**无条件**保护：即使关掉了"记录新拒绝"，历史账本文件仍在磁盘上，
> // 里面含着别的工作区/窗口的路径与 id（元数据）。实测踩过：只在 auditEnabled=true
> // 时才把它的路径交给判定 → 关掉账本开关后该文件就没人管了。`

同一个坑换了个入口又出现了一次：这次是**自定义路径**而不是**开关**。

**修法**：`selfRoots` 里把默认账本路径**恒常**并入，与自定义路径并存：

```js
const h = normalizePath(home).replace(/\\+$/, '')
const rs = [ state, rules ]
const def = `${h}\\subagent-shield-audit.jsonl`
const custom = normalizePath(auditFile)
rs.push({ path: def, label: '本插件的违规审计账本（默认路径）' })
if (custom && custom !== def) rs.push({ path: custom, label: '本插件的违规审计账本（自定义路径）' })
```

**回归测试**：`测试\unit.mjs` 的 `自定义 auditFile 时，默认账本路径仍受保护` 一项，修好后应变绿。

### 🔴 P2 —— 点名规则一多，判定耗时**严格线性增长**（性能悬崖）

**实测**（同机同进程，每档 5 批 × 20000 次摊薄计时噪声；规则形态 = `defaultPolicy:allow` + N 个窗口被点名 `true`）：

| 规则条数 | 单次判定（命中受保护文件） | 相对 25 条 | 读**无关**文件（对照组） |
|---|---|---|---|
| 0 | 5.1 µs | — | 4.6 µs |
| 25 | 7.4 µs | 1.0× | 4.7 µs |
| 100 | 31.2 µs | 4.2× | 19.9 µs |
| 400 | 152.8 µs | 20.8× | 19.2 µs |
| 1600 | 724.5 µs | 98.6× | 21.0 µs |
| **6400** | **3 646.6 µs（3.6 ms）** | **496×** | **20.8 µs** |

**结论：规则条数与单次判定耗时同比例增长（40× 规则 ⇒ 40× 耗时），是 O(n) 线性，不是 O(1) 查表。** 而读无关文件全程恒定在 ~20 µs —— 说明快路径没问题，问题只出在「被点名命中」的那条路径上。

另一次独立测量（用 `defaultPolicy:protect` 打底、10 条 → 5000 条）得到 **144×** 增长，与上表的线性结论一致。

**根因**（`lib/index.js`，`isProtected` 内）：

```js
const anyWin = Object.values(rules?.windows ?? {}).some(Boolean)
const anyWs  = Object.values(rules?.workspaces ?? {}).some(Boolean)
```

这两行**每次判定都重新铺开整个规则表**。而它们在同一个调用里还要被 `ancestorProtected()` 反复用到；在分支 `if (info.ws && has(rules?.workspaces, info.ws))` 里，`|| anyWin || dflt` 又是一次全表铺开。

**放大效应**：`effectiveStatus()`（`lib/index.js:252-254`）里也重算了 `Object.values(...)`，而 `listWindows()` 会对**每个**窗口算一次 `protected`，所以 1000 个窗口的 `/status` 请求 = 1000 × 全表铺开 = **10⁶ 量级**。

**为什么算缺陷而不算"可接受"**：设置页面的设计意图就是让人**逐条点名**（工作区列表 + 窗口列表 + 全开/全清）。一个"点名越多越慢"的实现，恰好惩罚它自己的主用法。1000 个窗口对本机来说并不夸张 —— 实测你的 `%DSH_HOME%` 已有 **164 个会话目录**，而 `listWindows` 只取最近 60 个，实际窗口数是这个的数倍。

**修法**：把 `anyWin / anyWs` 变成**派生缓存**，只在规则变更时重算（`loadRules()` / `saveRules()` / POST `/rules` 三处失效）：

```js
let agg = { anyWin: false, anyWs: false }
const recomputeAgg = () => {
  agg = { anyWin: Object.values(rules.windows).some(Boolean), anyWs: Object.values(rules.workspaces).some(Boolean) }
}
// isProtected 内部改用 agg.anyWin / agg.anyWs
```

改完应是**常数时间**（预计 6400 条也落在 ~7 µs 量级，退化 < 2×）。

**验收**：`测试\perf.mjs` H2 的 `规则从 10 条涨到 5000 条…增长` 一项，修好后增长应 < 2×。

### 🟠 P3 —— `/dsh-subagent-shield/status` 无鉴权，返回全部工作区路径与会话 id 清单

**实测**（沙箱实例，`cookie: ''`）：

```
GET /dsh-subagent-shield/status     →  HTTP 200
响应里含：workspaces[]（全部工作区编码目录名 + 解码后的可读路径）
          windows[]（最近 60 个会话 id + 所属工作区 + 时间）
```

`client.js` 的注释写的是「同源 + GUI cookie 鉴权」，但 `lib/index.js:647-650` 的 handler **没有任何校验**：

```js
disposers.push(child.webServer.register({
  kind: 'exact', path: STATUS_SRC,
  handler: (req, res) => { try { sendJson(res, 200, statusPayload()) } catch (e) { ... } },
}))
```

**影响范围要说清楚**（避免夸大）：这台机器上，本地任意进程本来就能读 `%DSH_HOME%` 的文件，所以它**不是**提权漏洞。它真正的意义是两点：

1. **它绕过了插件自己的规则**。如果 someday 用 `scope=all` + 逐窗口豁免把会话记录锁得很紧，这个接口仍然把清单交出去。插件成了自己的后门。
2. **它是"看不见的暴露面"**。用户以为"我保护了会话记录"，但一个 `curl http://127.0.0.1:3080/dsh-subagent-shield/status` 就拿到全部工作区与窗口清单。GUI 的 cookie 签名密钥本身就在 `.credentials.yaml` 里，而那个文件是同机可读的。

**修法**（三选一）：
- 首选：这个接口本来就只服务设置页，把它挂到 GUI 已有的鉴权中间件后面（照 `dsh-typing-guard` 等插件的做法）；
- 次选：`/status` 只返回**计数**（N 个工作区 / M 个窗口），明细改由需要鉴权的路径给；
- 兜底：至少不要返回**解码后的可读工作区路径**（`decodeWorkspaceLabel`）—— 那是纯泄漏增益，页面用编码名也能显示。

**附带**：`client.js:16` 的注释与实现不符，建议同步更正，否则下一个人会继续按注释放心。

## 三、设计待议（不是缺陷，但建议写进文档）

### 🟡 D1 —— 「身份不确定 ⇒ 先保守」这条规范，实测有**三格反例**（建议写进文档并钉一条测试）

我把这条猜错过两次（两次方向相反），最后用 **1152 组 sessions 叉乘 + 144 组 projcache 叉乘**与插件逐项对齐，才拿到确切语义。**以实测为准**：

| 输入（`defaultPolicy=allow` 且**无人被点名**） | 插件判定 | 直觉预期 |
|---|---|---|
| `{ws:'ws-alpha', sid:'sid-1'}` | 放行 | 放行 ✔ |
| `{ws:'ws-alpha', sid:'**'}` | **放行** | 有人会以为"通配=一批窗口"该拦 ✘ |
| `{ws:'**', sid:'sid-1'}` | **放行** | 有人会以为"工作区不确定"该拦 ✘ |
| `{ws:null 或 '' , sid:'sid-1'}` | **放行** | 同上 ✘ |
| `{ws:null, sid:null}`（纯目录级） | 放行 | 放行 ✔ |

**再叠加一层开关，上表立刻翻转**：只要 `defaultPolicy` 改回 `protect`，**或**点名保护任一工作区/窗口，上面每一格都变成**拦**。

**机制**（`isProtected` 实际逻辑）：`ws` 是非空字符串就落到"该工作区未被点名 ⇒ 查 `defaultPolicy`"；`'**'` 和 `''` 都是非空字符串，所以**不被当作祖先**。而 `{}` 空规则表 + `allow` ⇒ 祖先并集为空 ⇒ 放行。

**为什么这不算插件缺陷**：它与设置页那句「默认全部放行，只拦住下面勾选的」**字面一致**，也和规范 5「放行必须能追溯到一条用户显式允许」自洽（`allow` 就是那条显式允许）。而且真到这一步，`effectiveStatus()` 会给出黄字「会话记录与投影缓存实际未被拦截（只剩凭据受保护）」，不会静默。

**要改的只有文档**：《docs/说明书.md》§9.1 第 1 条现在写的是「任一身份不确定（通配 / 缺失 / 为空）⇒ 先保守，唯一例外是具体工作区被点名保护」—— 按实测，通配与缺失**并不触发保守**，触发条件是「回落到祖先并集后仍为空」。建议把 §9.1 那条改成实测语义，并在 `test-matrix.mjs` 里把这三格钉成显式用例（我这份 `测试\matrix.mjs` 的 A 层已经钉了，注释里写明"反直觉但实测为准"）。

### 🟡 D2 —— 目录级入口有 5 处放行，其中 1 处会暴露全部会话 id

只读采样真实 `%DSH_HOME%`：

| 目录 | 判定 | 说明 |
|---|---|---|
| `sessions` | 拦住 | 对 |
| `storages\session_projcache` | 拦住 | 对 |
| **`storages`（projcache 的父目录）** | **放行** | 列出即可得 `session_projcache` → **140 个会话 id**（实测条数） |
| `logs` | 放行 | 待确认是否含会话内容 |
| `cache` | 放行 | 同上 |
| `profiles` | 放行 | 含各 profile 的 `node_modules` 与补丁（元数据） |
| `DSH_HOME` 根 | 放行 | 会暴露 `subagent-shield-*.json` 的存在性 |

这与代码里既有的立场自相矛盾 —— `isProtected` 的注释写着：

> `目录列举本身也是信息泄露。`

**最小修法**：`classifyTarget` 里把 `${h}\storages` 本目录（`sid === null`）也归入 `projcache` 类，走祖先并集判定即可。

**其余 4 处**建议不做拦截（`logs`/`cache`/`profiles` 拦了容易误伤正常开发），但在 `README`「它保护什么」的表里**明确列出边界**，别让人以为整个 `%DSH_HOME%` 都被罩住了。

### 🟡 D3 —— 重复挂载会重复登记监听器（本机补丁确实登记了两次）

`%DSH_HOME%\profiles\web\cordis.patch.yml` 里 `dsh-subagent-shield` 出现了**两次**（`insert` 段一次 + 顶层行一次）。实测：`apply()` 被调用两次 ⇒ `tools/pre-execute` 上挂了**2 个**监听器 ⇒ 每次工具调用被判定 2 次。

**后果**：功能上不出错（重复 deny 无害），但 ① 每次调用白付一遍判定成本；② 将来若在监听器里加副作用（计数、写账本），会**双计**。

**修法**：装的时候保证只登记一条（安装器去重）；或 `apply` 里做幂等（用 `ctx.effect` + 一个模块级标记）。

## 四、性能实测（H 层）

| 场景 | 单次耗时（p50 / p95） |
|---|---|
| 拒绝路径（`read` 会话文件） | 17.5 µs / 21.0 µs |
| 放行路径（读工作区文件） | 18.5 µs / 19.5 µs |
| `glob` 通配会话目录 | 19.4 µs / 20.1 µs |
| 命令族（无命中） | 0.74 µs / 1.07 µs |
| **父会话（默认 `scope=subagents`）** | **0.13 µs / 0.24 µs** |

**结论：单次判定约 20 µs，相对一次工具调用（保守按 5 ms 估）占 0.42%，可以忽略。** 默认配置下父会话几乎零成本（0.24 µs），这个设计选择是对的。

| 其它开销 | 实测 |
|---|---|
| 冷挂载（读规则 + 读 810 KB / 4000 行账本 + 初始化） | **23 ms** |
| 挂载 vs 账本行数 | 0 行 11.8 ms → 1000 行 22.4 ms → 10000 行 34.4 ms → 50000 行 **106 ms**（线性，可接受；但账本无限增长会拖慢启动） |
| 会话树扫描（`/status` 每次刷新） | 540 目录 / 960 文件 → **65.5 ms**；真实 `%DSH_HOME%` 164 目录 / 142 文件 → **25.8 ms** |
| `/status` 端到端 | **107 ms** |
| 沙箱实例冷启动到监听 | **8.1 s**（DSH 本体开销为主，非插件） |
| 判定 20000 次期间的**真实 fs 读事件** | **0 次**（`diagnostics_channel` 抓 `fs/read`/`fs/readFile`/`fs/readdir`）→ 判定全程只读内存 |

**唯一需要盯的是 P2**：现在每次判定 ~20 µs 是因为规则表基本是空的（出厂 `defaultPolicy=protect` + 零点名）。一旦按设置页的设计意图逐条点名到 1000+，命中路径就是 **~500 µs ~ 3.6 ms**。

## 五、质量亮点（值得保留的做法）

1. **`deny` 理由里那句「请勿重试或用其它方式绕过」** 是全场性价比最高的设计。模型遇到权限错误的本能是换路径重试；这句话把它掐掉了。实测沙箱里被拒的调用**一次都没重试**。
2. **判定抛错一律放行**（I5）实测成立：用 getter 触发异常，结果 `allow` 且 `next()` 被调用，日志里有「判定异常（已放行）」。安全插件不该有能力搞挂工具管道。
3. **父会话默认豁免**（`scope=subagents`）是对的：否则事后审计做不了。而且它**真的**放行（父会话读会话文件 → `allow` + `next()`）。实测成本 0.13 µs，几乎白送。
4. **被 deny 的调用不碰磁盘**：实测被拒的文件内容在调用前后逐字节一致，且 20000 次判定零 fs 读事件 —— 拦截发生在**执行前**，语义正确。
5. **异常输入不崩**：`args=null`、`args='x'`、`name=42`、`file_path` 是对象、4000 段超长路径、含 `\0` 的路径 —— 全部返回 `null`（放行）而非抛错。
6. **账本四要素齐全**（`ts/tool/kind/window/caller/scope`），且 `window` 记的是**父会话 id** 而不是子代理自己 —— 这让"哪个窗口下的子代理在翻档案"可以被机械回溯。实测本机 41 条拒绝记录全部可回溯到具体父会话。
7. **`selfRoots` 对账本默认路径的兜底**（`normalizePath(auditFile) || 默认路径`）写得对 —— 正是这个兜底让 `auditFile` 为空白串时默认账本仍被保护。**注意 P1 正是这个兜底的"另一半"**：兜底只覆盖"空/未设"，不覆盖"设成了别的路径"。
8. **`classifyTargetLoose` 的宽松形状匹配**兜住了不少边角：实测 `.credentials.yaml.bak-*` 这类备份文件会被拦（我原以为它是缺口，跑完才发现被兜住了），`..\..\.dsh\sessions\**\*` 这种无 cwd 的相对逃逸也能识别。

## 九、测试方法论（含两次事故与最终护栏）

### 9.1 怎么拿到"机械可核验"的结论

| 手段 | 用途 |
|---|---|
| **独立重写的真值机**（`oracle.mjs`，不 import 插件） | 判定预期值的唯一来源；拒绝"跑一遍看看结果" |
| **全叉乘穷举** | 配置 × 身份 × 工具位 × 路径形态 = 18000 组；语义层另有 1152 + 144 组 |
| **批量摊薄计时** | 每档 5–12 批 × 20000 次，折算单次纳秒，避免单次计时噪声 |
| **`diagnostics_channel` 订阅 `fs/read` 等** | 证明"判定不碰磁盘"（20000 次判定零 fs 读事件） |
| **被拒文件逐字节比对** | 证明拦截发生在**执行前**，不是"执行后报错" |
| **真启动 + HTTP 实测** | 沙箱 profile 加载插件、起监听、`/status` 真实响应与鉴权实测 |
| **落盘 `results.json`** | 全部 183 项的逐条结果与明细，可复核 |

### 9.2 两次真实事故（以及为什么最后是三层护栏）

**必须如实记录：评审过程中我的测试脚本两次真的改到了插件本体。**

| # | 事故 | 根因 | 处置 |
|---|---|---|---|
| 1 | 护栏自检脚本把 `plugin\` 目录**整个删掉** | 第一版护栏用 `process.getBuiltinModule('node:fs')` 打补丁，但 `import 'node:fs'` 拿到的是**只读 ESM 命名空间**（赋值会 `TypeError`），我的补丁落在另一个对象上 —— 六笔写全部穿透 | 从 `%DSH_HOME%\profiles\web\node_modules\dsh-subagent-shield` 恢复（事故前已用 SHA256 证明与发布目录**逐字节相同**），逐文件核验一致 |
| 2 | `fs.promises.writeFile` 把 `lib\index.js` **截成 0 字节** | 修好同步方法后**漏了 `fs.promises` 这一族** | 同样从已装副本恢复，`index.js` 哈希回到基线 `03AAF9E1…D69A68` |

**事故性质**：两次都是"**护栏本身没生效**"，而不是测试内容有害。这正是"护栏必须自检"的实证 —— 一个没验证过的护栏等于安慰剂，而且会让人更放心地去冒险。

**最终护栏（三层 + 自检）**：

1. **JS 写拦截**：补丁 `fs` 默认导出对象上的同步方法**与 `fs.promises`**，再调 `syncBuiltinESMExports()`，让 `import 'node:fs'` / `import fs from 'node:fs'` / `require('fs')` **三条路**都生效。自检 14 笔应拦的写 **14/14 拦住**（含事故那一笔 `rmSync(pub, {recursive:true})`），7 笔正常沙箱读写 **0 误伤**。
2. **装载器自检**：复制插件到沙箱时禁止目标落在插件目录内；`cpSync`/`copyFileSync` 只判目标，源为插件目录是允许的只读复制。
3. **跑前跑后全量 SHA256 快照比对**（文件集合 + 哈希 + 大小 + mtime）：即使前两层被绕过，也一定**查得出来**。

**流程保障**：`run-all.mjs` 先跑 **Z0 护栏自检，不通过就拒绝执行其它层**；**Z 层比对放在 `finally` 里**，所以即使中途崩溃，也一定会给出"插件本体是否被动过"的结论。

**被放弃的一层**：曾想加 Windows ACL（`icacls /deny`）做 OS 级禁令，但本沙箱里 `icacls` 连 `/grant` 都返回 `Access is denied`，**物理上改不了权限**，故删除 —— 不留"以为有、其实没有"的假护栏。
