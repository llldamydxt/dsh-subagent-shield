# 硬隔离怎么做（"有心"场景的唯一正解）

> 面向的场景：你要跑**对抗性验证**，或者实验结论会被认真对待 —— 此时"子代理会不会偷看"
> **不能**建立在"它答应不偷"上。
>
> 先说结论：**插件这一层做不到**（原因见 §1）。真隔离只能换**安全主体**。
> 本文给三条路、每条的代价、以及**怎么验**。

---

## 1. 为什么插件做不到（有源码依据，别再往这方向投时间）

`dsh-subagent-shield` 是**工具层策略围栏**：它拦的是"子代理通过工具去读"。而子代理可以**自己写代码读盘**。

宿主的文件沙箱能帮忙吗？**不能** —— 我查过 `@deepseek-ai/dsh-sandbox-policy` / `dsh-sandbox-local` / `dsh-sandbox-windows-acl`：

| 证据 | 内容 |
|---|---|
| 模式文案 | `read-only` / `workspace-write` / `danger-full-access` 三种模式**全都只谈"修改文件"** |
| Windows 后端自述 | *Windows ACL **write-restriction** sandbox backend (restricted-token spawn with capability-SID **write** allowlist)* |
| Windows 链的模块文档 | *"...**reads stay unconfined**..."* |
| 源码关键词 | `file-write*` 3 处 · **`file-read` 0 处** |
| Linux | Landlock：整盘 `readOnly` + 仅工作区可写 → 读不受限 |
| macOS | seatbelt：`allow default` + `deny file-write*` → 只禁写 |

⇒ **子代理读得到盘是设计如此。** 不是配置错，也不会因为"插件再改改"而消失。

## 2. 三条路（按"能不能真隔离"排序）

### 路 A：不同 OS 账户（本机可行，但**需要管理员**）

原理：Windows 默认 ACL 让 `C:\Users\<别人>\...` **只有本人和管理员可读** →
两个 DSH 实例跑在不同账户下，各自的 `DSH_HOME` 天然互不可读 ✓（读也读不到，不靠任何脚手架）。

```powershell
# 需要管理员 PowerShell。以下为示意，执行前先看懂每一步。
net user dsharm1 <密码> /add                      # 建臂账户
net user dsharm2 <密码> /add

# 用另一个账户跑 DSH（GUI 会开在各自会话里）
runas /user:dsharm1 "cmd /c set DSH_HOME=C:\Users\dsharm1\.dsh && dsh ..."
```

**要解决的三个实际麻烦**：

| 麻烦 | 解法 |
|---|---|
| 任务书怎么给进去 | 放一个**公共目录**（如 `C:\DSH-实验\输入\`），对两个臂账户只给**读** |
| 产物怎么收回来 | 每臂一个目录 `C:\DSH-实验\输出\臂A\`，ACL 只给「臂A 账户 + 你的账户」**写+读**；臂B 账户**不给**任何权限 |
| 你怎么审计 | 你的账户对两个输出目录都有读权限（或在 ACL 里给自己读）→ 父侧审计照常 |

> ⚠️ 关键：**输入目录只读、输出目录不互相授权**。只做"不同账户"而把产物写进同一个公共目录，
> 等于没隔离（臂A 仍能读臂B 的产物）。

### 路 B：容器 / 虚拟机 / Windows 沙箱

- 每个臂一个容器（或一个 VM），只挂载**该臂的**输入目录与自己那一个输出目录。
- **成本**：要装（WSL2 / Docker / Hyper-V / Windows 沙箱都要**管理员 + 可能重启**）；
  容器里跑 DSH 还要处理 GUI/端口转发。

### 路 C：另一台机器（最省事，也最可靠）

- 两个臂在**两台机器**上跑，各写各的盘；产物用一个共享盘/网盘目录回传（**分目录、不互相授权**）。
- **成本**：一台旧笔记本就够；网络与依赖要一致（这可能成为新的混淆变量，需在报告里写明）。

## 3. 这台机器的现实（2026-10-12 实测）

```
当前用户        <机器名>\<你的账户>   ← **不是管理员**
本地用户        只有 1 个启用（Administrator / Guest / WDAGUtilityAccount 全禁用）
Windows 沙箱    无    WSL 未安装    Docker 未安装
DSH_HOME        环境变量 DSH_HOME 可覆盖（默认 ~/.dsh）→ 起第二个实例没问题
```

⇒ **现在三条路都走不了**：建用户 / 装 WSL / 开沙箱**都需要管理员**。

**你能做的**：
1. **拿到管理员权限**（本机管理员账户当前是禁用的）→ 然后走路 A（最轻）
2. **换一台机器**走路 C（不需要本机管理员）
3. 接受现状：用 `dsh-subagent-shield` + [提示词模板](提示词模板.md) 跑**非对抗性**实验，
   并在报告里写明"隔离是工具层策略，未做对抗性隔离"

## 4. 怎么验"真隔离成立"（无论走哪条路）

**必须在 OS 层验，不能问子代理"你有没有偷看"。**

1. **控制组**：臂 A 的子代理读**自己** `DSH_HOME` 的会话记录 → **应当成功**
   （否则你测的是"环境坏了"，不是"隔离成立"）
2. **实验组**：臂 A 的子代理读**臂 B 的** `DSH_HOME\sessions`（用工具 + 用命令两种）
   → **都应当失败**，而且失败原因是 **OS 拒绝（权限/Access denied）**，不是插件的【已隔断】
3. **看错误文本**：
   - 出现 `Access is denied` / `Permission denied` → **OS 层隔离成立** ✅
   - 出现【已隔断】→ 那只是插件在拦，**不算硬隔离**
4. **反向对照**：臂 B 的子代理读臂 A 的 → 同样应当被 OS 拒绝（双向）
5. 记进实验记录：哪个账户、哪条路径、错误原文、时间

> 第 3 条是这套验证的关键分界：**"被插件拦住"和"被操作系统拦住"是完全不同的两件事。**

---

## 5. 一句话

> **一个用户下的所有进程，读权限是一样的 —— 插件再怎么写，也只是在这一层做策略。**
> **真隔离 = 换安全主体（账户/容器/机器）+ 各自独立的 `DSH_HOME`。**
